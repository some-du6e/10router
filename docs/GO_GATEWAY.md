# Go gateway

A Go process in front of the Node app server. It takes over the hot inference path one route at a time and relays everything else to Node. Phase 1, this document's first deliverable, ships proxy mode only: the gateway relays every request and serves nothing itself. `GATEWAY_MODE=off` is the default, and with it the container runs exactly as before.

Why Go: all of Node's request handling (body parsing, rewriting, SSE relay) runs on one JS thread. On a busy install that one thread is what saturates first, however many cores the box has. The hot path parses 1 to 4 MB JSON bodies, rewrites them and relays SSE. Go can spread that over every core and allocate far less per request.

The code is in `gateway/`, a Go module. Phase 1 used only the standard library. Phase 2b adds the one planned dependency, `modernc.org/sqlite`, for `internal/db`.

## Process layout

One container, two processes.

```
client ──► :20128  10router-gateway  (PID 1, Go)
                     │  relays over loopback, peer handed over in headers
                     ▼
           127.0.0.1:20129  node custom-server.js  (child of the gateway)
                     │
                     ▼
           DATA_DIR/db/data.sqlite   (shared from phase 2; Node owns the schema)
```

- `scripts/docker-entrypoint.sh` fixes ownership of `/app/data` and `/app/data-home` as before. With `GATEWAY_MODE=proxy` or `native` it then runs `su-exec node /app/gateway/10router-gateway -- node custom-server.js`. Any other value, unset included, runs `su-exec node node custom-server.js`, which is what the old inline entrypoint did. An unknown value logs a warning and runs Node alone.
- The gateway listens on `HOSTNAME:PORT` (default `0.0.0.0:20128`, what Node used). An IPv4 address opens an IPv4-only socket, as Node's does. Go's plain `tcp` on `0.0.0.0` would also listen on IPv6.
- It starts the command with `PORT=$GATEWAY_APP_PORT` (default 20129), `HOSTNAME=127.0.0.1`, `KEEP_ALIVE_TIMEOUT=30000`, a fresh random `GATEWAY_PEER_TOKEN`, and `GATEWAY_MODE` set to the mode it parsed (`proxy` or `native`), so Node never reads the raw value its own way. The rest of the environment passes through unchanged.
- The gateway binds its port only after Node accepts connections, so a client during boot gets a refused connection, as it does today, instead of a 502.
- Node's stdout and stderr are the gateway's, so the container log is unchanged. Gateway lines start with `[Gateway]`.
- If Node exits on its own (a crash, an OOM restart, the updater), the gateway exits with the same code, so the restart policy sees what it sees today. A killed Node reports 128 plus the signal, the way a shell does.
- On Linux, Node gets `SIGKILL` if the gateway dies without stopping it (parent-death signal), so a crashed gateway can't leave a Node process holding the database.
- The data dir is still `.9router` and the compose volume is still `9router-data`.
- The gateway reaps only its own child. That matches today, where Node as PID 1 doesn't reap orphans either.
- Memory: the gateway's RSS is in the bench job's output. A container memory limit (cgroup `memory.max`), if there is one, now covers both processes.

`GATEWAY_MODE=off` leaves nothing of the gateway running. The entrypoint never starts it. If someone runs the binary with `off` anyway, it `exec`s the command in its own place.

## Modes and settings

| Variable | Default | Meaning |
|---|---|---|
| `GATEWAY_MODE` | `off` | `off`: Node alone on `PORT`. `proxy`: the gateway relays everything. `native`: proxy plus the routes the gateway serves itself. This build has none, so it relays everything as `proxy` does and logs that. It also opens the database once Node listens, runs the schema guard and keeps the config snapshot current (see "Phase 2b"), which only the health endpoint and the log show. |
| `GATEWAY_SHADOW` | unset | CI only. `1` with `GATEWAY_MODE=native`: Node still serves every request, and the gateway compares the upstream request its native route would send for each `/v1/messages` with the one Node sent (see "Phase 2c", part 3). `0` or unset is off; any other value, or `1` with another mode, is off with a warning. It also stays off, with a log line, when `HOSTNAME` isn't `0.0.0.0`, `::`, `127.0.0.1` or `::1` (Node reports over loopback) or when the gateway didn't start Node itself. |
| `GATEWAY_APP_PORT` | `20129` | Node's loopback port. If it equals `PORT`, `PORT+1` is used. |
| `KEEP_ALIVE_TIMEOUT` | `5000` | The public idle keep-alive timeout, read the way Next's standalone `server.js` reads it: `parseInt`, and anything not positive leaves the default. |
| `SHUTDOWN_DRAIN_TIMEOUT_MS` | `180000` | Parsed exactly like `server-drain.js` does. Both processes read it. |
| `TRUST_PROXY` | unset | Read by the client-IP rule, the same value Node reads. |
| `GATEWAY_PEER_TOKEN` | random | Leave it unset; the gateway makes one per boot and gives it to Node. A value under 32 characters stops the gateway from starting. custom-server.js acts on it only while `GATEWAY_MODE` is `proxy` or `native`, so a token left in an env file does nothing once the mode is back to `off`. |
| `GATEWAY_INFLIGHT_BODY_BUDGET_MB` | `256` | Native requests' bodies the gateway's memory gate admits at once, times `GATEWAY_BODY_COPIES`. Shrunk at startup when it and Node's `INFLIGHT_BODY_BUDGET_MB` don't fit under 80% of the container's memory (see "Phase 2c"). `0` turns the budget off. Read once phase 2c wires the native route; no effect in this build. |
| `GATEWAY_BODY_COPIES` | `1` | Copies of each body the gate counts against the budget, 1 to 16. Same status as the budget. |
| `GATEWAY_MEMORY_HIGH_WATER_MB` | 80% of `memory.max` | The container's anonymous memory (both processes) above which new native requests wait. Unset with no container limit: off. `0` turns it off. Same status as the budget. |

The request-body timeout (300 s) and headers timeout (60 s) are Node's defaults, which nothing in this repo changes, so they are constants rather than settings. The header size cap follows Node's `--max-http-header-size`, from `NODE_OPTIONS` or the node command line (which wins).

The binary always starts Node itself (`10router-gateway -- node custom-server.js`) and refuses to run without a command. Relaying to a Node started some other way can't prove that both sides hold the token, and a Node without it would take every relayed client for a local one.

Phase 2 adds `GATEWAY_NATIVE_ROUTES` (for example `POST /v1/messages`) and `GATEWAY_NATIVE_PROVIDERS` (provider node ids or prefixes such as `openai-compatible-chat-*`). Both are allowlists: a request is native only if its route and every provider it could reach are listed. Everything else is proxied.

The fallback rule: when in doubt, proxy to Node. In phase 2 the gateway proxies whenever:

- the mode is `proxy`, or the route or provider isn't allowlisted;
- the database schema is newer than the gateway understands (see below), or Node runs on `sql.js` (which Node itself refuses in native mode, so this is a driver recorded by an earlier run);
- `gateway/GATEWAY_PROXY_ONLY` lists a package;
- the gateway hits anything it doesn't model yet: a setting it can't read, a combo strategy it doesn't port, an endpoint override it can't apply, a client format it doesn't parse.

It may hand a request to Node until the first response byte has gone to the client. It keeps the request body bytes, so the handoff replays them unchanged. After the first byte there is no handoff, and the gateway owns the error, exactly as Node does today.

## Proxy mode in detail

`gateway/internal/proxy` wraps `httputil.ReverseProxy`.

- **No buffering.** Request bodies stream to Node as they arrive, and `FlushInterval: -1` flushes every chunk Node writes. One SSE event goes out as one flush. A test holds back the second megabyte of a 4 MB body until the upstream reports it has the first, so a proxy that buffered would deadlock there.
- **Headers pass through.** That covers `Authorization`, `x-api-key`, `anthropic-beta` and everything else. `Host` is the client's, because Node's origin checks, tunnel detection and local-client rule read it. `ReverseProxy` drops `Forwarded`, `X-Forwarded-For`, `-Host` and `-Proto` before `Rewrite`, and any header a client names in `Connection`. The gateway puts every header in custom-server.js's `FORWARDING_HEADERS` back as the client sent it and adds none of its own, since Node's rule decides whose forwarding headers count. Node never honoured `Connection` tokens, so a client can't use them to strip a front proxy's `X-Real-IP`.
- **The request target is the client's.** `ReverseProxy` re-escapes the path (a `\`, which Node's URL parser reads as `/`, would arrive as `%5C`) and re-encodes a query that has a `;` or a bad `%` escape, which drops those parameters and sorts the rest. The gateway sends the original path and query. `OPTIONS *` goes to Node too, not to `net/http`'s built-in empty 200. Two exceptions: a path starting `//` keeps `ReverseProxy`'s escaping (sent raw it would read as an authority), and Go's server answers `400` to a path with a malformed `%` escape before the gateway sees it.
- **Header size.** The gateway caps a client's headers at about Node's `--max-http-header-size` (16 KiB, or whatever `NODE_OPTIONS` or the node command line sets), instead of Go's 1 MiB. It counts every raw byte where Node counts only names, values and the URL, so it is stricter by a few bytes per header. Behind the gateway, custom-server.js gives its server 4 KiB more than the flag, room for the peer headers, so the gateway is the one that answers `431`.
- **Header count.** Node takes 1000 header lines by default and can drop the rest without a word (versions differ, so the design doesn't count on a refusal). `net/http` writes headers sorted by name, so the peer headers go out near the end, where a dropping Node would lose them to a client's padding. The gateway answers `431` above 990 lines. Node also treats a gateway-less loopback request at its cap as `unknown`.
- **No content sniffing.** Go's server would guess a `Content-Type` for a reply Node sent without one. The gateway turns that off, so the header is Node's or absent.
- **Hop-by-hop headers stop at the gateway in both directions.** These are `Connection` and the headers it lists, `Keep-Alive`, `Proxy-Connection`, `TE` (except `trailers`), `Transfer-Encoding` and `Upgrade`. `Expect: 100-continue` is answered by the gateway and not sent on.
- **No transparent gzip.** The loopback transport has `DisableCompression`, so the client's own `Accept-Encoding` reaches Node untouched. Node compresses or doesn't, as before. The transport also ignores `HTTP_PROXY`, which 10router users set for upstream calls.
- **Timeouts are never shorter than Node's.** The gateway sets no write timeout and no response-header timeout, so streams can run 10 minutes and more. Node sends early SSE headers after 30 s and owns the 240 s upstream headers limit. The request-body bound runs as a read deadline that lifts as soon as the body has been read, so it never cuts a response. A body that misses it gets Node's bare `408` and the upstream request is cancelled.
- **Loopback pool.** Up to 256 idle connections to Node, idle timeout 20 s, with 32 KiB read and write buffers each (16 MiB if all 256 sit idle). Node's keep-alive on that hop is 30 s, so the gateway always closes an idle connection first and never sends a POST on a socket Node is closing at that moment. Such a POST could not be retried.
- **Client aborts.** A client that disconnects cancels the request context, the transport closes the connection to Node, and Node sees `close` and stops the upstream call. A test checks this end to end.
- **WebSocket.** `ReverseProxy` relays `Upgrade: websocket` and splices the two connections after Node's `101`. The Codex bridge runs in Node unchanged. `ReverseProxy` copies from the raw hijacked connection, so bytes a client sends right behind its upgrade request would stay in the server's read buffer and be lost. Codex sends its `response.create` frame that way, without waiting for the 101. The gateway hands `ReverseProxy` a connection that reads through that buffer first.
- **h2c.** custom-server.js serves an `Upgrade: h2c` request (JBR sends them) as the HTTP/1.1 request it also is, and closes the connection afterwards. The gateway does the same before relaying, so Node never sees the upgrade.
- **Node unreachable.** The gateway answers `502` with `{"error":{"code":"gateway_upstream_unavailable",...}}` and `Retry-After: 1`. If Node fails mid-stream, the gateway aborts the client connection, as a destroyed Node socket would.
- **Absolute-form request targets** (`POST http://host/v1/...`). The authority becomes `Host`, as RFC 9112 says it must. Node used the `Host` header instead, but no real client sends absolute-form to an origin server.

Next builds `request.url` from its own listen address and port, not the `Host` header. Behind the gateway that is `127.0.0.1:20129` instead of the 20128 address, so a route that takes an origin from `request.url` (SAML metadata without a base URL, for one) gets the loopback one. Neither is a public address, so set `BASE_URL` for those either way.

Header name casing on responses changes, because Go canonicalizes names. HTTP/1.1 header names are case-insensitive, and the e2e compares bodies, not header spelling.

## Client IP

custom-server.js decides who a request comes from. Forwarding headers count only from a loopback peer or a peer `TRUST_PROXY` lists, and every other peer is its socket address. Rate limits, the login limiter, keyless local `/v1` and audit logs all depend on that.

Behind the gateway, Node's TCP peer is always the gateway on loopback. Without help, every request would look local. So the gateway hands the real peer over:

- On every request it deletes any client copy of `x-9r-gw-token`, `x-9r-gw-peer-ip` and `x-9r-gw-peer-port`. It then sets them to its token and the address and port of the connection it accepted. An IPv4 client of an IPv6 listener is written `::ffff:a.b.c.d`, the spelling Node's socket would report.
- custom-server.js removes the three headers from every request. When `GATEWAY_PEER_TOKEN` is set, the socket is loopback, the token matches (constant-time compare) and the IP parses, it uses the handed peer in place of `req.socket.remoteAddress` for everything: `isOnThisMachine`, `clientKeysFor`, `isTunnelTraffic`, the `x-9r-socket-ip` and `-port` stamps, and the Codex WebSocket bridge's peer. The token leaves `process.env` at boot so Node's children don't inherit it. With `GATEWAY_MODE=off` the variable is unset and none of this code runs.
- It fails closed. A loopback request that carries any of the headers but can't prove them (wrong token, no token, a peer that isn't an address) gets the peer `unknown`, which is never this machine. Falling back to the socket would make it local, since behind the gateway the socket is always loopback. For the same reason the gateway refuses to start with a token shorter than 32 characters, or without a Node command of its own.
- A request that reaches Node's loopback port directly, from inside the container, carries none of the headers and is treated as it is today: a loopback client. That covers the Codex bridge's own POST and Node's self-calls.

The rule itself runs unchanged in Node. `gateway/internal/clientip` is a Go port of it (`isLoopbackHost`, `isOnThisMachine`, `clientKeysFor`, `isTrustedProxyPeer`, `isTunnelTraffic`), down to JavaScript quirks such as `Number("")` being 0 in a `TRUST_PROXY` prefix. In phase 1 it only decides who sees the health endpoint's counters. Phase 2's native routes use it. Both implementations are held to one table, `gateway/internal/clientip/testdata/parity.json`. `go test` reads it, and so does `tests/unit/gateway-clientip-parity.test.js` against custom-server.js. A rule change in one place fails the other until the table and both ports agree.

## Graceful drain and shutdown

The gateway follows `server-drain.js`, and Node runs its own drain alongside.

1. On the first `SIGTERM` or `SIGINT`, the gateway logs `[Gateway] SIGTERM: draining N in-flight request(s)...` and marks itself draining. It passes the signal on to Node 250 ms later, so a request it admitted just before has reached Node by the time Node closes its listener and idle connections.
2. `http.Server.Shutdown` closes the listener, so new connections are refused. It also closes each keep-alive connection as it goes idle.
3. A request that still arrives on an open connection gets the same `503` JSON body (`server_draining`), `Retry-After: 5` and `Connection: close`. An upgrade gets the bare `503`.
4. The never-ending dashboard streams (`/api/usage/stream`, the console-log stream, MCP SSE) close at once.
5. Model traffic holds the drain. The gateway counts it with the same path rule as `MODEL_TRAFFIC`, including dot segments, percent-decoding and absolute-form targets. The Go tests use the same cases as `tests/unit/server-drain.test.js`. WebSocket connections don't hold the gateway's drain. A Codex turn holds Node's drain, and the gateway waits for Node.
6. The gateway exits when its own model requests are done and Node has exited, after a 200 ms flush. It exits with Node's exit code.
7. A repeat signal soon after the first is the same stop arriving twice (`npm`, a supervisor and a `kill` can all send one). Node ignores a repeat within 1.5 s of the signal it got, and that one arrived 250 ms late, so the gateway ignores repeats within 1.75 s of its own. A later repeat goes on to Node, which then exits at once; the gateway gives it 2 s and exits 1.
8. The gateway's deadline is the drain timeout plus 3 s. Node's own timeout fires first, then its listeners get their 2 s. After that the gateway kills Node and exits 1.
9. `SHUTDOWN_DRAIN_TIMEOUT_MS=0` stops both at once, as before.
10. `SIGHUP`, `SIGQUIT`, `SIGABRT`, `SIGUSR2` and `SIGPIPE` are ignored. As PID 1 with no handler on them, Node ignored the first four too, because the kernel drops a default-action signal to a namespace's init. Go's runtime would otherwise exit on them with no drain, and passed on, their default action would kill Node, which is no longer PID 1. A broken log pipe must not end the gateway. `SIGUSR1` (Node's inspector) goes on to Node, unless Node runs with `--disable-sigusr1` (then it is ignored too). So does the signal of a heap-snapshot or diagnostic-report handler (`--heapsnapshot-signal`, or `--report-on-signal`/`--report-signal`, default `SIGUSR2`, in `NODE_OPTIONS` or on the command line) when it is `SIGUSR2`, `SIGHUP` or `SIGQUIT`.
11. Node runs in its own process group, so a terminal's signals (`docker run -it`) reach only the gateway. Ctrl-C drains as above. Ctrl-\ (`SIGQUIT`) follows item 10: ignored, unless a Node report or heap-snapshot handler is on it, as with Node as PID 1.

Docker's `stop_grace_period` must still exceed the drain timeout. The compose file's 3m30s does.

## Health

`GET /_gateway/health` never reaches Node. It answers `200 {"status":"ok","mode":"proxy","app":"up"}`. It answers `503` with `"draining"` during a drain and `"app_down"` when Node's port refuses a connection. That probe is cached for 1 s. A client on this machine, by the client-IP rule, also gets `inflight`, `uptimeSeconds`, `version` and `goroutines`.

In `native` mode the body also has `"native": "ready"` or `"native": "off"`, and with `off`, for a client on this machine, a `nativeReason` such as `schema version 7 is newer than this gateway knows (6)`, `GATEWAY_PROXY_ONLY lists combo, ...` or `the app server runs on sql.js, ...`. Native routes being off never fails the check: everything is proxied then. With `GATEWAY_SHADOW=1`, a client on this machine also gets `shadow`: the shadow compare's counters, decline reasons and latest differences (see "Phase 2c", part 3).

## SQLite sharing (phase 2)

Phase 1 doesn't open the database. From phase 2 both processes share `DATA_DIR/db/data.sqlite`. Usage tables live in that same file, because `usageRepo` uses the same adapter.

**Driver.** `modernc.org/sqlite`, pure Go, because the image is Alpine and the gateway is built with `CGO_ENABLED=0`. It is the only planned dependency. It is slower than C SQLite on heavy queries, but the hot path runs a handful of indexed lookups and short writes.

**Pragmas.** These match `src/lib/db/schema.js`: `journal_mode=WAL` (Node sets it, and it persists in the file), `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`. The gateway keeps one writer connection and a small reader pool. It also sets `wal_autocheckpoint=0`, since SQLite would otherwise checkpoint on the committing connection, and opens the file read-write without create (`mode=rw`), so it never makes a database Node hasn't.

**Node's transactions are `BEGIN IMMEDIATE`.** A deferred transaction that reads before it writes (`updateSettings`, `updateProviderConnection` and every other read-merge-write repo) can't wait for another process's write lock. SQLite skips the busy handler when a reader upgrades, so it fails at once with `SQLITE_BUSY`. The better-sqlite3, bun:sqlite and node:sqlite adapters therefore begin their outermost transaction `IMMEDIATE`, and nested calls stay savepoints. With one process this changes nothing. `tests/unit/db-shared-file.test.js` holds the lock from a second process and fails with deferred transactions. The pre-migration backup (`backupDbLite`) is the one exception and keeps a deferred `BEGIN`: it only reads `main` while it copies into an attached file, and an IMMEDIATE one would write-lock `main` for the whole copy.

**Rules for sharing the file:**
- Every write is a short `BEGIN IMMEDIATE` transaction that reads the row fresh and changes only the fields the gateway owns. Node's `better-sqlite3` waits on a lock synchronously, on its main thread, for up to 5 s. A gateway transaction held long therefore freezes the whole Node event loop.
- The gateway leaves Node windows to take the lock. SQLite has no queue for its write lock: a waiter polls, sleeping 1 to 100 ms between tries, and the lock goes to whoever asks while it is free. A gateway that began its next write as soon as the last committed would win every time. The first stress run showed that: Node's writes waited out the full 5 s and failed, with event-loop lag at p99 over 5 s, while every gateway write landed. So all the gateway's writes go through one goroutine (`writer.go`). It puts every write queued at that moment into one transaction, each in its own savepoint so a failure undoes only itself. It stops taking more after holding the lock 10 ms (`MaxWriteHold`), and leaves the lock free at least 25 ms (`WriteGap`) before it begins again. Usage rows are also batched every 100 ms.
- No read transaction stays open. Node runs `wal_checkpoint(TRUNCATE)` every 60 s, and a long-lived reader stops the checkpoint and lets the WAL grow. The gateway's connections never checkpoint (`wal_autocheckpoint=0`). The one exception is the gateway's last close after Node has exited, when SQLite checkpoints on its own.
- If Node runs on `sql.js` (in memory, rewriting the whole file), the file can't be shared. Node records its driver in `_meta.dbDriver` each time it opens the database, after its migrations (`recordDriver` in `driver.js`; sql.js writes it to disk with its next save). The gateway stays in proxy mode unless it is `better-sqlite3`, `bun:sqlite` or `node:sqlite`, and re-checks when that row changes. The schema guard also refuses a file that isn't in WAL mode. Node, for its part, never falls back to sql.js while `GATEWAY_MODE` is `native` (`sharesFileWithGateway` in `driver.js`): with no native driver it fails to open the database, with a message saying how to fix that, rather than rewrite the file over the gateway's writes (`tests/unit/db-driver-chain.test.js`).

**What the gateway reads and writes:**

| Table | Reads | Writes |
|---|---|---|
| `_meta` | `schemaVersion`, `configGeneration`, `dbDriver` | `totalRequestsLifetime` (increment, in the usage transaction) |
| `settings` | the JSON row | never |
| `apiKeys` | key lookup, policy (budget, allowlist, expiry) | `spentUsd`, `requestCount`, `lastUsedAt` (in the usage transaction) |
| `combos` | by name | never |
| `providerNodes` | `openai-compatible` nodes (prefix, baseUrl, apiType, modelRoutes, droppedBetas, overrides) | `droppedBetas` (merge) |
| `providerConnections` | active connections with `data` | in `data` only: `modelLock_*`, `modelLimit_*`, `modelNoHeaders_*`, `providerReset_*`, `backoffLevel`, `lastError`, `lastErrorAt`, `errorCode`, `testStatus`, the `authFail*` streak fields, `authDemote_*` (compare-and-swap, as Node does) and `authDemoteOkAt`, `lastUsedAt`, `consecutiveUseCount`, `providerSpecificData.droppedBetas` (merge); and auto-disable: the `isActive` column with `autoDisabledAt` and `autoDisabledReason` |
| `proxyPools` | by id | never |
| `kv` | scopes `modelAliases`, `pricing`, `customModels` | never |
| `usageHistory` | never | insert |
| `usageDaily` | the day's row | read-modify-write of the day's JSON aggregate |
| `requestDetails` | never | upsert, only when observability is on |

Everything else is Node's alone: management keys, audit, notification channels, migrations, OAuth tokens and their refresh.

**Schema ownership.** Node's migrations own the schema. The gateway never creates or alters a table. Node opens its database, and on a fresh install creates and migrates it, on its first use of it, which can come after it listens. So the gateway opens the file once Node listens, keeps trying every second until it exists, and the schema guard tells an unmigrated file apart. The gateway is built with a manifest: the highest migration number it knows (`_meta.schemaVersion`, which counts migration files, 6 today) and the columns it uses in each table. `SCHEMA_VERSION` in `schema.js` (stored as `_meta.backupSchemaVersion`) also moves on purely additive table changes, so the column check, not that counter, is what catches those. At startup, and whenever `PRAGMA schema_version`, `_meta.schemaVersion` or `_meta.dbDriver` changes, the gateway checks `_meta.schemaVersion` and `PRAGMA table_info`. A newer version or a missing column switches native routes off. Everything is proxied, the health endpoint says why, and one line is logged. Extra tables and columns are fine, because `syncSchemaFromTables` only adds. A migration that changes a column the gateway reads must bump the manifest in the same PR, and CI runs the gateway's schema check against a database migrated by that PR's Node.

## Config sync (phase 2)

Node caches settings for 5 s with an in-process generation counter. It reads connections, combos, nodes, API keys and aliases from the database on every request. A second process can't see an in-process counter, so:

- Node bumps `_meta.configGeneration` in the same transaction as every write to `settings`, `combos`, `providerNodes`, `apiKeys`, and the `kv` scopes `modelAliases`, `pricing` and `customModels`. It also bumps it on dashboard edits of `providerConnections`, but not on the lock and usage writes the hot path makes. The bump is `bumpConfigGenerationSync` (or `writeConfig`) in `src/lib/db/helpers/configGeneration.ts`. A connection write bumps when `connectionConfigChanged` finds a change outside the runtime fields (locks, errors, auth evidence and demotions, rotation, the top-level token fields, auto-ping stamps). A key turned off, which changes the `isActive` column, counts. A token refresh doesn't, even when it rewrites `providerSpecificData`: `updateProviderCredentials` (`src/sse/services/credentialSave.js`) passes `tokenRefresh`, and the fields its result writes (the tokens, a project id, the `providerSpecificData` keys its patch sets) are runtime for that write (`refreshedFields`). The gateway reads connections fresh at pick time, so a reload would buy nothing. The gateway bumps the same way for its own config writes: a node's `droppedBetas`, a connection's `providerSpecificData.droppedBetas`, and an auto-disable.
- `tests/unit/config-generation.test.js` lists every SQL statement in `src/` and `open-sse/` that writes one of those tables, by file and function, with whether it bumps or why it needn't (usage spend, migrations, kv scopes the gateway doesn't read). A new write fails it until it is listed. Each listed site that bumps is then run on sql.js, node:sqlite and better-sqlite3 through an adapter that checks every config write has a bump in its own transaction, and the lock, usage and token-refresh writes are checked to leave the generation alone.
- The gateway polls `PRAGMA data_version` every 250 ms. That pragma changes when another connection commits, and costs no I/O. When it changes, the gateway reads `configGeneration` and reloads its snapshot if that changed too. The usage writes on every request change `data_version` but not the generation, so they cost one indexed read.
- On top of that, a 5 s TTL caps how stale a snapshot can get, the same bound Node's own settings cache has today.
- Per-request state stays per request: locks and demotions are read fresh from `providerConnections` at pick time, as Node reads them.

## Phase 2b: the database layer

Status: built and tested, serving nothing. `gateway/internal/db` is the driver, the pragmas, the schema guard, the watcher and the typed readers and writers for the table above. In `native` mode the gateway opens the database once Node listens, checks it and keeps the snapshot current, and health and the log report the result. Nothing calls the writers yet; phase 2c's native route will. Production runs with `GATEWAY_MODE` off, so none of this runs there.

**Schema guard.** `manifest.json` (embedded) holds the highest migration the gateway knows, the drivers it shares a file with, and the columns it reads in each table. `DB.Check` refuses, with a reason, a file whose `_meta.dbDriver` is sql.js, missing or unknown, one not in WAL mode, a `_meta.schemaVersion` above the manifest's, or a table without a column the manifest lists. Extra tables and columns pass. The watcher re-runs the check whenever `PRAGMA schema_version`, `_meta.schemaVersion` or `_meta.dbDriver` changes, and every 5 s while it refuses. It logs one line per change of answer. `tests/unit/gateway-db-manifest.test.js` holds the manifest to `schema.js` and the migration list, and holds the Go tests' schema (`testdata/schema.sql`) to the statements migrations run. A new migration therefore fails CI until the manifest says the gateway can read it.

**JSON.** Rows the gateway rewrites go through `internal/db/jsjson`, which parses and prints JSON as `JSON.parse` and `JSON.stringify` do. Object keys keep their order, with array-index keys first, as V8 orders them. Numbers are printed as `Number#toString` prints them, and strings are escaped as JavaScript escapes them, a lone surrogate (an error message cut in the middle of an emoji) included. A row the gateway writes is the text Node would have written, unknown fields included.

**Writers.** Each reads its row fresh inside the writer's `BEGIN IMMEDIATE` transaction and changes only what it owns. Callers wait for their own write. A write is reported failed only if it didn't land: when SQLite rolls a whole transaction back (an I/O error, a full disk), every write in it fails and the rest wait for the next. A write whose context ends before it starts is skipped, and when the lock doesn't come within the busy timeout, every write queued then fails at once rather than each waiting 5 s. A usage row that can never be written (a value the JSON writer refuses) is dropped and counted rather than holding the rows behind it. The price of the pacing is latency, not throughput: a write that arrives just after a commit waits out the gap, so one waits up to about 35 ms (25 ms gap, 10 ms hold), and under load many share each transaction. Phase 2c's lock writes should not sit on a request's critical path.

- `UpdateConnection(ctx, id, ConnectionUpdate)` is `updateProviderConnection` for the hot path's options: `Set` (owned fields only; anything else is `ErrNotOwned`), `AutoDisable` (only while another connection of the provider is on), `Demote` (compare-and-swap on the `JSON.stringify` of the record, plus `probeNow`), `LiftDemote`, `NoteServed` and `APIKeyUsed` (a key pasted in since drops the streak, the turn-off and the demotion). It writes `data`, `isActive` and `updatedAt` and returns the merged row.
- `MergeDroppedBetas(ctx, connectionID, nodeID, betas, ownBaseURL)` is `saveDroppedBetas`: the union rule of `sanitizeNodeQuirks`, on the connection's `providerSpecificData` and the node.
- `WriteUsage(ctx, entries)` writes many requests in one transaction: their `usageHistory` rows, each day's `usageDaily` aggregate read and written once, `_meta.totalRequestsLifetime` and each key's spend. The result is what `saveRequestUsage` gives for them one at a time, float rounding included. `NewUsageWriter` batches `Add`ed rows every 100 ms. Local dates use the process's zone, as Node's `Date` does; the binary carries its own zone data.
- `SaveRequestDetails(ctx, rows, maxRecords)` is the request-detail flush: upsert, full copies on the newest 25 rows only, trim to `maxRecords`. It takes payloads already capped.

**Readers.** `ListConnections(ctx, provider, active)` sorts as `getProviderConnections` does, `ConnectionByID`, `APIKeyByKey` (fresh, for spend), `NodeByID`, `ProxyPoolByID`, `APIKeys` and `Nodes`. Each type's `NodeObject()` is the object Node's repo returns for the row.

**The snapshot API for 2c.**

```go
path, err := db.DataFile(os.Getenv)                     // DATA_DIR/db/data.sqlite, as Node resolves it
d, err := db.Open(path, db.Options{})
err = d.Watch(ctx, db.WatchOptions{OnStatus: logIt})   // first check and load, then every 250 ms
st := d.Status()                                        // Ready, Reason, SchemaVersion, Driver
s := d.Snapshot()                                       // nil unless Ready
s.Settings.Truthy("requireApiKey")                      // getSettings(), defaults merged, retired keys dropped;
                                                        // Truthy for `if (settings.x)`, Bool for `=== true`
s.Combos["name"]; s.Nodes["openai-compatible-chat-…"]   // by name, by id
s.APIKeys["sk-…"]                                       // policy; spend via d.APIKeyByKey
s.Alias("sonnet"); s.Pricing; s.CustomModels
```

A snapshot is immutable; `Watch` swaps in a new one when `configGeneration` moves, and at least every 5 s. Phase 2c should hold one snapshot per request.

**For 2c, on Node's side.** Node's in-process caches keyed on `connectionsVersion()` and `combosVersion()` (auto-combo, the Codex catalog) don't see the gateway's writes. Once the gateway turns keys off, those caches should also watch `_meta.configGeneration`.

## State that lives in Node's memory

Most routing state lives only in Node process memory today: rotation, prompt-cache affinity, the per-provider selection mutex, auth evidence, hung-model state, memory admission and the request-detail buffer. The 429 locks and demotions are in the database and need no change. The design keeps each piece of memory state in one process by routing whole providers. A provider allowlisted for native chat sends all its chat traffic through the gateway, so the gateway alone holds:

- prompt-cache warm keys (`open-sse/services/cacheAffinity.js`),
- the selection mutex and round-robin stickiness (`src/sse/services/auth.js`),
- auth evidence and spread leases for dead-key demotion (`auth.js`, `spreadLeases.js`),
- model-hang state (`open-sse/services/modelHang.js`),
- combo rotation (`open-sse/services/combo.js`),
- its own memory admission gate.

The dashboard reads some live state from Node's memory: pending counters, the recent-requests ring, `lastUsed` indexes and the usage event stream. Node will tail `usageHistory` by rowid every second to fold in rows the gateway wrote. That needs no new IPC, and the rows are the source of truth anyway. "Recent requests" per endpoint and the pending counters for gateway traffic are to come through a loopback endpoint on Node, `POST /api/internal/gateway/events`, batched every 250 ms. If it's down, the dashboard loses a live view, never a usage row. The endpoint exists since phase 2c part 3 with one event, `betas-learned`, sent one per call while the gateway waits; it takes only a request from this machine carrying the peer token in `x-9r-gw-events-token` (see part 3).

## Parity testing

Nothing turns native until it matches Node byte for byte on recorded traffic.

1. **Golden fixtures from the Node path.** A recorder captures, for each fixture request:
   - the client request;
   - the exact upstream request Node sent: URL, headers (keys redacted), body bytes;
   - the upstream response;
   - the bytes Node wrote to the client;
   - the database writes, as row diffs.

   Fixtures come from synthetic bodies shaped like production: 50 to 1,000 messages, 12 to 48 tools, thinking blocks with signatures, `cache_control` in every position, images, `tool_result` with `is_error`. Later phases add the e2e mock upstream. Every value is synthetic, with no real keys, hosts or prompts.

   In place for `internal/claudeprep` (phase 2a), the request half:
   - **Corpus.** `tests/helpers/claudeprepCorpus.js` generates the cases. Its JSON writer can emit what `JSON.stringify` never does: `1.0`, `1e3`, big integers, duplicate and integer-like keys, escapes, CRLF and tab whitespace, and invalid UTF-8 bytes. The large corpus also runs every capability family against every thinking intent and every `(level)` suffix.
   - **Recorder.** `tests/unit/gateway-claudeprep-parity.test.js` is part of the default vitest suite. 2. **Transform tests.** The Go request preparation runs on every fixture's client body and must produce the same upstream body bytes as Node. JSON key order and number formatting count, because the upstream's prompt cache keys on bytes. This is where most of phase 2's risk sits.

   For `internal/claudeprep`:
   - `TestParityWithNode` requires the exact URL, header list and body bytes for every fixture Node prepared.
   - It requires a decline, with the reason the generator names, for each case marked `expectDecline`, and a decline for each case Node threw on or refused. Any other decline fails.

3. **Byte-level SSE comparison.** Mock upstream response in, client bytes out. Event framing, `[DONE]`, keepalive comments, early headers at 30 s, error events after early headers, and usage extraction must all match. Generated ids and timestamps are normalized first. The other e2e suites don't run with it yet.
5. **Canary in production.** `native` mode with the route allowlisted for one provider node whose keys are few. Compare usage rows, error rates and cache-hit rates against the other nodes for a day, then widen.

### Phase 2a: `internal/claudeprep` (done)

The request rewrite is ported and held byte-identical to Node. Nothing calls it yet, so production is unchanged.

`claudeprep.Prepare(body []byte, in Inputs) (*Request, error)` takes the client's body bytes and returns the upstream request Node would send: the URL, the headers object in Node's key order and spelling, the body bytes, and whether the upstream is asked for SSE. It runs the same steps in the same order as Node:

1. chat.ts: the `[1m]` marker, `speed`/`service_tier` for a budgeted key, `model` set to `<node>/<model>`.
2. chatCore: the limit-hold notice, the model's Messages route (`modelRoutes`), the provider-level thinking override, the upstream `stream` flag, client detection, and unsupported media replaced with placeholders.
3. translateRequest, Claude to Claude: `normalizeThinkingConfig`, tool-call id repair, stubs for missing tool results, `applyThinking` from the model's capabilities, the Claude Code prompt for OAuth tokens, then `prepareClaudeRequest` (max-tokens clamp, blank system and message drops, `cache_control` reset and re-placement, tool ordering and same-role merges, the prefill repair, tool filtering, folding and schema typing, the tool-choice relax).
4. chatCore again: translator-only fields, the upstream model id, `dedupeTools` for Claude Code, `type: "custom"`.
5. DefaultExecutor and the endpoint overrides: headers (auth, the client's `anthropic-beta`, learned and first-party flag drops, identity presets, header lines), the URL query override, the `temperature` strip, beta-gated body fields, the reasoning placeholder some models need, the body overrides, then `finalizeBody`.

The body is edited as a `Value` tree with JavaScript's semantics, never `map[string]any`. Objects keep JavaScript's key order: array-index keys first, ascending, then insertion order, and a repeated key keeps its first slot. Strings are UTF-16 code units held as WTF-8, so a lone surrogate survives. Numbers are float64 and are written back the way `Number#toString` writes them. `JSON.stringify` doesn't keep a client's spelling, and the port matches Node's bytes, not the client's: `1.0` goes out as `1`, `1e3` as `1000`, an escaped `é` as the character itself, and a big integer loses the same digits it loses in Node. A client that already sends `JSON.stringify` output, which Claude Code does, gets its own bytes back. The body is decoded the way `request.text()` decodes it: a BOM is dropped and each ill-formed UTF-8 sequence becomes one U+FFFD.

The capability tables (capabilities.js, thinkingLevels.js, the vision name patterns, the identity presets, the beta-flag field tables) and the constants Node exports (the default max tokens, the level budgets, the API version and host, the Claude Code prompt, the continuation texts, the limit-hold sentinel, the GA thinking displays, the web search tool type) aren't restated in Go. `gateway/internal/claudeprep/tables.json` is exported from Node and embedded, and the Node parity test fails when the export is stale.

Whatever the port doesn't model it hands back with a `*DeclineError` (`claudeprep.IsDecline`), and the gateway proxies that request. That covers:

- any input on which Node would throw, such as a null content block or a non-string `text`, and a connection Node refuses (`blockedReason`);
- a level or effort that names an `Object.prototype` member (`constructor`), which Node's table lookups would find;
- JSON nested more than 512 deep (Node's own recursion fails a few thousand down);
- header values that aren't printable ASCII without edge spaces: fetch sends Latin-1, throws on CR, LF and NUL, and trims, while net/http refuses other control characters;
- the web search tool, which needs Node's built-in search hooks;
- mid-conversation `tool_addition`/`tool_removal` blocks, the client's or a body override's;
- a top-level `allOf`/`anyOf`/`oneOf` or `$ref` in a tool's `input_schema`, which Node flattens;
- a `json_schema` `response_format`;
- non-ASCII model ids and client-identity headers;
- base URLs that aren't plain `http(s)://host[:port]/path?query`: no scheme, a port fetch blocks, dot segments, backslashes, bad escapes, characters the URL parser would percent-encode, IPv6 or underscore hosts. `Request.URL` is the string Node hands fetch; 2c's sender normalizes host case and a default port, as fetch does;
- providers other than `openai-compatible-*`, and models not routed to the Messages API.

### Phase 2c: the native hot path, proven in shadow mode

Phase 2c builds the remaining packages and wires them into a native `/v1/messages` that runs only as a shadow in CI (`GATEWAY_SHADOW=1`): Node serves every client, the gateway works out the upstream request it would send for the same input and diffs it against the one Node sent. It landed in three PRs: the request checks; combo fallback, accounts and the sender; then the native route's plan and the shadow itself. The stream, usage and the native serve that sends come next.

**Refusals are Node's.** A native request goes through the same checks as one Node serves, but the gateway never answers a refusal itself. Any body Node answers with a 400, any request it answers without calling an upstream (the Claude Code bypass), any key it refuses (401, 402, 403), and anything the gateway can't decide exactly, is a decline (`internal/decline`; `decline.Is` also recognizes claudeprep's `DeclineError`), and the request goes to Node with its bytes unchanged. A check in Go may be stricter than Node's, never looser. The tests hold that both ways: each case Node serves must be served too, unless the fixture says why Go declines it on purpose (`conservative`). So the gateway needs no copy of Node's error bodies, and it touches no in-memory state Node would have touched for them.

**Part 1 (built, serving nothing; only the shadow compare calls these packages, so none of their settings has an effect outside it):**

- `internal/route`: `Match` takes only `POST` to `/v1/messages`, `/v1/v1/messages` and `/api/v1/messages` (the `next.config.mjs` rewrites onto `/api/v1/:path*`, which the fixture records), in origin form. A trailing slash, a doubled slash or an escape goes to Node. `Inspect` parses the body as `readJsonObject` does (with claudeprep's parser) and gates the shape: an object with a printable-ASCII `model` that is still non-blank after the `[1m]` strip, `stream: true`, and a non-empty `messages` array of objects. It then runs `handleBypassRequest`'s decision, including the inputs it throws on, over the client's `User-Agent` values joined. Node's HTTP parser keeps only the first `User-Agent`, so joining them declines whenever any copy would make Node answer itself. The skip patterns come from `tables.json`, exported from `SKIP_PATTERNS`. Its callers pass `ccFilterNaming`, and clientauth's callers `requireApiKey`, by the setting's truthiness (`Settings.Truthy`), as Node reads both.
- `internal/clientauth`: `ExtractKey` reads `Authorization: Bearer`, `x-api-key` and `x-goog-api-key` in Node's order. A repeated key header, a non-ASCII key, and a request that would fall back to `?key=` are declined. `Check` refuses management keys, needs the client on this machine (the client-IP rule, with no `Origin` and no cross-site `Sec-Fetch-Site`) or an active key (a CLI token alone is Node's), applies `requireApiKey`, then the expiry (only the `toISOString` form is parsed), the model allowlist (`IsModelAllowed`, a port of keyLimits.js's, over aliases and combo members; fusion combos, non-ASCII entries, a `comboStrategies` that isn't an object and an allowlist checked without the combo and alias lookup are declined) and the budget (a spend column holding text, which Node's `Number()` may read as a number, is declined; a spend of NaN, from an infinite total less an infinite offset, is 0 as in `budgetState`). It returns the key, its row and `HasBudget`.
- `internal/combo` (resolution so far): `ParseModel`, `ModelInfo` (`getModelInfo`: a provider prefix through the custom nodes in table order, reserved built-in prefixes, combos before aliases, string and object aliases, the inferred provider) and `ComboModels`. A combo with a non-string member, or members stored as a string or an object, is declined. So is an id or alias that names an `Object.prototype` member or isn't printable ASCII, since Node's object lookups and `toLowerCase` read those differently, and any alias lookup while a stored `__proto__` alias is an object: `kvStore.getAll` builds the alias map by assignment, so Node inherits from it. `tables.json` is Node's registry-derived data (provider aliases, reserved prefixes, built-in model aliases, `MAX_COMBO_DEPTH`), exported, never restated. `FromSnapshot` builds the config from a 2b snapshot, which now keeps the nodes' table order (`NodeOrder`) and a combo's stored `models` as Node reads it, array or not.
- `internal/admission`: the gateway's own gate. It counts each body once (`GATEWAY_BODY_COPIES`, default 1) against `GATEWAY_INFLIGHT_BODY_BUDGET_MB`, queues FIFO for `INFLIGHT_QUEUE_WAIT_MS`, and answers with Node's 503 `overloaded_error` and `Retry-After: INFLIGHT_RETRY_AFTER_S` (the shared variables, with Node's defaults from `tables.json`). A body without Content-Length counts as `INFLIGHT_UNKNOWN_BODY_MB` until it has been read. Nothing in flight always goes in. Its high water is the container's anonymous memory (cgroup `memory.stat`, so both processes) plus three times the bodies not yet replying, since the bytes read, claudeprep's tree and the bytes it builds are all alive while a request is prepared. `FitBudget` shrinks the budget, and logs why, until it and Node's `INFLIGHT_BODY_BUDGET_MB` fit under 80% of `memory.max`, down to 32 MB.
- `gateway/files.go` embeds `GATEWAY_PROXY_ONLY` and `node-map.json`; a listed package turns native off. A `node-map.json` that isn't valid JSON, or lists no package, also turns native off with a reason; proxy mode still serves (`TestCorruptNodeMapLeavesTheRelayServing`).

**Part 2 (built, serving nothing):**

- `internal/combo` `Plan` and `Run`: handleRoutedChat and routeSingleModelChat up to the account loop, then handleComboChat's fallback. `Plan` walks the whole member tree before anything is sent and declines what Node would refuse or route by state Go doesn't keep: a bare id that is no user combo (an auto combo may form), a member Node answers with a 400 (no provider and no combo, an id `modelIdProblem` refuses, a combo nested in itself or past `MAX_COMBO_DEPTH`), a provider that isn't an openai-compatible node, the fusion and round-robin strategies, the limit hold (global or the key's), a Codex client (whose limit failures `finalizeRoutingError` rewrites), the web search tool (Node's side-search hooks), and a request that may need a model capability. That last check (`MayNeedCapability`) is on the safe side of `detectRequiredCapabilities`: the capacity adapter and the auto-switch reorder read the model catalog, which part 3 ports, and with no capability required both change nothing. `Run` first runs `Env.Preflight` on every provider and model the tree reaches: `accounts.CheckProvider` declines a strategy it doesn't serve (soonest-reset, a value that isn't a string, a sticky limit that isn't a number), and on each active key stored fields Node reads its own way, demotion records and any base URL outside a plain allowlist (an ASCII host, a port with no leading zero, path segments and a query of unreserved characters, no `.` or `..` segment), where net/url and WHATWG URL could differ; its per-key check is `upstream.PreflightKey`: `upstream.Preflight` (an endpoint's Timeout, Retries or Proxy setting, the TLS variables, the Settings outbound proxy, a route that isn't direct) and a dry run of the attempt's own `Prepare` for the key and model (a key with no credential, a model not routed to the Messages API, any other setting `Prepare` refuses); the dry run and the send must build their `Inputs` with the same function. So a decline over configuration comes before anything is sent or written. `Run` refuses to run without a preflight. `Select` runs the cheap check again on each pick before it writes or returns it (`LoopInput.Check`), so a row changed mid-request still can't send where Node wouldn't. Then it tries each member in order, waits out a cooldown of 5 s or less on a 502, 503 or 504, and ends with Node's `{error:{message}}` and its status rule. No member reply carries a `retryAfter`, so the combo never answers with `unavailableResponse`. Every reply Go gives comes from an upstream or from account state, never from a refusal. What only a send can show (a 401 or 403, a network error, a redirect) hands the request to Node after Go's own attempts and lock writes, before any byte reaches the client: Node then routes it over the rows as Go left them, as it would after another request locked those keys.
- `internal/accounts`: `Select` is getProviderCredentials for an openai-compatible node's keys (fill-first, round-robin with stickiness, warm-key preference and the warm wait, the every-key-locked answer); `MarkUnavailable` and `ClearError` write markAccountUnavailable's and clearAccountError's fields through 2b's writer; `RunModel` is chat.ts's account loop with model hang, the header-timeout and same-request-error stops, and the failure summary. A key with a demotion record and the soonest-reset strategy are declines. A 401 or 403 before the first byte hands the request to Node (`Handoff`), which keeps the dead-key evidence. On success `RunModel` clears the key's error itself, as chatCore's `onRequestSuccess` does when the stream starts. As in Node, a failure after the client left locks nothing (the loop checks first); a hang-up that lands while a lock, counter or clear is being written doesn't cancel that write. The sender reports each send's headers budget through the attempt's `onBudget`, which restarts a probe's lease as `noteProbeBudget` does. Each `RunModel` call is its own request for model hang (Node's `randomUUID()` per routeSingleModelChat), so a combo that reaches one model twice counts twice. Model hang's probe lease follows `ModelHang.BudgetMs`, which part 3 sets from `upstream.HeadersBudget`, so the env overrides apply as in Node. The loop's `Reply.Response` is the Response Node builds (errorResponse or unavailableResponse, headers and body). `KeysShareOneUpstream` takes the transport from the sender's route. As in Node, a round-robin pick writes its counters while it holds the provider's lock; through 2b's paced writer each write takes up to about 35 ms, so one round-robin provider makes at most about 30 picks a second. The canary should watch that before a busy round-robin provider goes native.
- `internal/upstream`: `ResolveRoute` is resolveConnectionProxyConfig (the account's pool or Direct, its legacy URL, the provider's, Global's, else the system), and `Transport` is networkPath's key. Only a Direct route, or the system layer with no `HTTP(S)_PROXY`/`ALL_PROXY` applying after `NO_PROXY`, is sent; a pool, relay, legacy proxy or blocked route is a decline, and so are the Settings outbound proxy (Node writes it into its own process's `HTTP(S)_PROXY`, which the gateway can't see), an endpoint's Timeout, Retries or Proxy setting and the TLS variables Node reads (`NODE_EXTRA_CA_CERTS` and the like, `CheckTLSEnv`). `Preflight` checks all of it per key. `Sender` sends HTTP/1.1 with fetch's wire defaults (`accept: */*`, `accept-language: *`, `sec-fetch-mode: cors`, `user-agent: node`, `accept-encoding: gzip, deflate`, or `br, gzip, deflate` over https, `connection: keep-alive`, repeated names joined with `", "`), undici's 10 s connect timeout (TCP and TLS together), 300 s body timeout, 4 s idle keep-alive and 16 KB response-header limit. The names and values match Node's; the order is Go's client's (an upstream reads headers by name). A header undici refuses or takes over (`host`, `transfer-encoding`, `keep-alive`, `upgrade`, `expect`, `content-length`, a `connection` other than `keep-alive`), which an endpoint's header lines could add, is a decline (`CheckHeaders`, in `PreflightKey` and again in `Send`). The request goes to `claudeprep.CanonicalURL(Request.URL)`, the URL fetch sends (`new URL(...).href`: the host lowercased for `Host` and SNI, a default port dropped). A gzip body is decoded as it is read, so a slow first event isn't a headers timeout, and as zlib reads it: a member's decoded bytes come back as soon as they are decoded, a body that ends before its trailer or inside the next member's header reads as far as it got, a zero byte after a member ends the body (whatever follows), another member is read on, and any other byte after a member fails the read as zlib does (an error body then reads as `""`, so the failure is `[status]: HTTP status`). `Execute` is DefaultExecutor.execute: the headers budget (`UPSTREAM_STREAM_HEADERS_TIMEOUT_MS` parsed as `envMs` does, `parseInt` included) and its timeout text, the per-status retries of `DEFAULT_RETRY_CONFIG` with the same bytes, then up to `MAX_BETA_RETRIES` resends without the flags a 400 named, each re-running `Prepare` with them in `Connection.Node.DroppedBetas` (the last with `StripBeta`). A failure is chatCore's `[status]: <body text, or "HTTP status">`, the body decoded as `Body#text()` decodes it (gzip, a BOM dropped, WHATWG replacement), and `HTTP <status>` when reading it fails, as chatCore takes `""` when `text()` throws. A redirect, a 421, a status Node's `Response` can't carry a reply with (below 200, above 599, 204, 205, 304), a network error, an encoding other than gzip and an error body over 8 MB hand the request to Node. An error never quotes the request URL, whose query may hold a key. Learned flags go to `LearnedBetas` (not when the last retry ran out of time: Node throws there and saves nothing). Node writes them (`saveDroppedBetas` changes config rows and the generation), so part 3 passes them on through its events endpoint, and merges them into the key's settings for its next attempt in the same request (`MergeDroppedBetas`), as Node's re-read of the row would have them.

Each of the three packages reports a bad embedded table through `Ready()` instead of panicking at start (claudeprep and route too, since part 3); the native route checks them all.

**Part 3 (wired, in shadow only):**

- `internal/native` is the native `/v1/messages` up to the send. `Plan` runs `route.Inspect`, `clientauth.Check`, `combo.Plan` and, on every provider model the tree reaches, the preflight (`accounts.CheckProvider` with `upstream.PreflightKey`). `Prepare` is the one builder of `claudeprep.Inputs` for a key and leaf, used by the preflight's dry run and by the send: the client's headers as Node's `request.headers` folds repeats (the first `User-Agent`, cookies joined with `; `, others with `, `), the key's `HasBudget`, `settings.providerThinking[provider].mode` (a shape Node would read its own way is a decline), and the key's `apiKey`/`accessToken`. Its `Accounts` has `ModelHang.BudgetMs` set from `upstream.HeadersBudget(env, true)`, so `UPSTREAM_STREAM_HEADERS_TIMEOUT_MS` moves a probe's lease as in Node. `native.Ready()` joins `claudeprep.Ready()`, `route.Ready()`, `combo.Ready()` (which folds in `accounts.Ready()`) and `upstream.Ready()`: the gateway links all of them in every mode, so none of these panics at start on a bad embedded table (`internal/db`'s schema manifest, linked since phase 2b, still does); health reports native off with the reason when any fails.
- `claudeprep.FileCatalog` is `catalogOverride.js`: `DATA_DIR/model-catalog.json` (beside the database's directory), re-read when its mtime changes, empty when it is missing or `JSON.parse` would throw. `Prepare` reads it through `NewModels` as `capabilities.js`'s `refine` does: a modality turns on only for an exact `true`, `maxOutput` counts when positive, lookups by base id, and an `Object.prototype` name finds an entry that holds nothing. Shapes `sync.js` never writes (an array where an object goes, a `maxOutput` that isn't a finite number) decline. `gateway-catalog-parity.test.js` records Node's lookups and `getCapabilitiesForModel` over 34 catalog files and 13 model ids (`testdata/catalog.json`). Requests that may need a capability stay declined (`combo.MayNeedCapability`): routing by the catalog is still Node's. The native route prepares through `claudeprep.DeclineCovered(FileCatalog)`, which declines a request whose model the catalog gives a `maxOutput` or a modality. The shadow e2e showed why: Node's request handlers don't read the catalog at boot. `src/instrumentation.js` installs the source in its own module copy of `capabilities.js`, and the route handlers' copy gets one only once `POST /api/models/catalog-sync` runs a sync in them (an API call; the dashboard doesn't make it). So whether Node clamps `max_tokens` to the catalog depends on the process's history, and Go can't know it. A modality matters even though capability requests are declined: `stripUnsupportedModalities` keeps or replaces media in earlier turns and tool results by it, and `MayNeedCapability` reads only the current turn. The catalog is consulted only from `refine`: for models without an exact hand-table entry, pattern matches included. That has a coverage cost the canary should weigh. Node's sync writes models.dev modalities by model id, and for ids such as `claude-haiku-4-5` that match a pattern rather than an exact entry, the catalog turns on `pdf`, which the pattern leaves off. So once a synced catalog exists, those models go to Node on every request, media or not. A narrower rule (decline only when the body carries a block of a kind the catalog turns on) would keep parity and serve more, but it belongs in `Prepare` rather than behind the `Catalog` interface. Making Node read the catalog from boot (a source shared across module copies) is a production behavior change that hasn't been made; once it is, `DeclineCovered` can give way to `FileCatalog` itself.
- `internal/nodeevents` hands Node the writes Node makes itself. Learned beta flags (`upstream.Input.LearnedBetas`, through `Native.LearnedBetas`) go to `POST /api/internal/gateway/events` on Node's loopback port, which calls chat.ts's `saveDroppedBetas` with the stored connection, so Node's union, serialization and config generation apply. The gateway waits for the answer, as `DefaultExecutor` awaits `onBetasRejected`, and only logs a failure. The route (`src/lib/gatewayEvents.ts`) is public in the dashboard guard and checks for itself: a request from this machine (`isLocalRequest`) carrying `x-9r-gw-events-token` with the peer token, which custom-server.js verifies (`globalThis[Symbol.for("10router.verifyGatewayToken")]`) without exposing it. Anything else is a 404. With `TRUST_PROXY=true` no request is local, so the route refuses the gateway too and learned flags only log a failure; native serving (which sends, and so learns) will need the token alone there.
- `internal/shadow` is `GATEWAY_SHADOW=1` (with `GATEWAY_MODE=native` only, CI only). For each request `route.Match` takes, the gateway reads the body (64 MB at most; a larger one is relayed as is), removes any `x-9r-shadow-id` the client sent, runs `native.Plan`, and tags the relayed request with a fresh `x-9r-shadow-id`. custom-server.js runs a request the gateway proved (the peer token) and tagged inside an `AsyncLocalStorage` holding the id, and `proxyAwareFetch` hands each send to the observer, which posts the URL, the headers object's entries in order and the body to `/_gateway/shadow` on the gateway's port with the peer token (`GATEWAY_SHADOW_URL`, which the gateway sets; loopback only). The gateway takes a report only from a loopback peer with the token. For each send of a planned request it prepares the attempt for every planned key whose credential Node's headers carry and requires one to equal Node's send byte for byte (URL, header names and values in order, body). It counts requests, planned, declined (by reason), sends, matched, differed, unplanned (sends of a request Go declined), unknown, sends missing for a planned request (2 s after the response ends) and errors, and shows them under `shadow` in the health endpoint for this machine's clients; each difference is logged with URL queries and every header value outside a short list of the preparation's own non-secret headers left out (the ±60 bytes of body around a body difference are quoted, so the mode is for CI's synthetic requests). The report carries the body as the executor passed it, a Buffer of the exact bytes, and a send that passes through `proxyAwareFetch` twice (a second copy of `proxyFetch.js` patched `fetch` over the first) is reported once. A request whose first send matches a combo member after the plan's first counts as `reordered`, which the e2e (whose upstream never fails) requires to be 0. The gateway removes a client's `x-9r-shadow-id` from every relayed request, not only the ones it shadows. It never sends upstream and never writes the database. `shadow.sh` (in `gateway.yml`'s e2e job) runs the built image that way over the claudeprep corpus's requests and two combos, and fails on any difference, any planned request Node didn't send for, or a report count that isn't the upstream's request count. Not compared yet: which key Node picks (the compare takes any planned key whose credential Node's send carries), a send prepared from a row Node rewrote between its send and the report (Go reads the rows when the report arrives), async work a shadowed request starts that outlives it (it keeps the request's id), sends after the request is scored (`unknown`), the resend after a beta 400 (it would show as a difference), the stream and usage.

The recorders behind part 2 run Node's real `handleChat` with only `proxyAwareFetch` replaced (`gateway-combo-fallback-parity.test.js`: 18 routing scenarios, every attempt, wait, reply and connection row compared, a 401's handoff included), or with nothing replaced against a local scripted server (`gateway-upstream-parity.test.js`: 19 wire scenarios, every request's header names and values and body compared). The fetch defaults over https, which the plain-http server can't show, come from Node's own fetch through a dispatcher that sends nothing. Waits run on a fake clock; the fixtures name no real host.

Each package has a Node recorder (`tests/unit/gateway-<pkg>-parity.test.js`) that runs Node's real code over a synthetic corpus and writes `gateway/internal/<pkg>/testdata/`. The clientauth, combo and accounts recorders insert their keys, combos, nodes, connections and aliases as rows of a real Node database (sql.js), have Node's repos read them, and record the rows; the Go tests load the same rows into their own SQLite file and read them through the gateway's readers (`APIKeyByKey`, `LoadSnapshot`, `FromSnapshot`). Settings are the exception: each case's `requireApiKey` and combo strategies go to Node through `updateSettings` and to Go as a settings object built for the case. Each case Go declines on purpose names words its decline must contain, so it can't pass by declining for another reason. The route tests also run every streamed body in the 2a corpus through the gate. Each package also has a `Gateway <pkg> parity` workflow that checks Node still makes those files and runs the Go tests on them. `<PKG>_RECORD=1` (`ROUTE_RECORD`, `CLIENTAUTH_RECORD`, `COMBO_RECORD`, `ADMISSION_RECORD`, `ACCOUNTS_RECORD`, `UPSTREAM_RECORD`) rewrites them; `COMBO_RECORD` covers both combo recorders (`resolve.json`, and `fallback.json` with `capabilities.json`).

### Risks

- **Byte-exact request preparation.** A one-byte difference in the upstream body can silently halve prompt-cache hits and double cost. The transform tests run over a large corpus and the shadow compare runs before any canary. The Go JSON handling must produce `JSON.stringify`'s bytes: JavaScript's key order, number text and string escapes. So it edits a tree with JavaScript's semantics and never round-trips through `map[string]any`. Phase 2a does this; see above.
- **SQLite lock contention freezing Node.** Covered by the short-transaction, paced-writer and no-open-reader rules above. The `Gateway DB` workflow's stress job hammers both processes and fails if Node's event-loop lag reaches 50 ms at p99 (see "Verifying phase 2b").
- **Split memory state.** If a provider is half native and half proxied, for example during a rollout or when a request falls back to Node, the two processes keep separate affinity and evidence maps. Cache affinity then gets worse for those requests, and dead-key evidence builds more slowly. Locks are unaffected because they live in the database. Rollouts flip a provider whole.
- **Drift as Node changes.** Every PR that touches a file in the map above must update the Go port or mark the route proxy-only. `gateway/node-map.json` lists the Node files each package ports, `claudeprep`'s in full (more than the table's row: every helper the port mirrors). The `Gateway drift` workflow (`scripts/gateway-drift-check.mjs`) runs on every PR and fails one that changes a listed file unless the PR changes that package too (`gateway/internal/<pkg>/`, re-recorded fixtures included) or `gateway/GATEWAY_PROXY_ONLY` lists the package. It also fails when a listed file no longer exists, when a mapped package has no `gateway-<pkg>.yml` parity workflow, or when that workflow's path filter misses a listed file. The gateway also embeds `GATEWAY_PROXY_ONLY` (`gateway/files.go`): every mapped package is on the native `/v1/messages` path, so a listed one turns that route off, and health says which package did. The parity fixtures catch what that misses: a behavior change in a file the map doesn't list breaks `tests/unit/gateway-claudeprep-parity.test.js`, or one of the recorders that run the whole request path (`gateway-combo-fallback-parity.test.js`, `gateway-upstream-parity.test.js`), all of which run in every vitest run.
- **Two memory budgets under one container limit.** Admission budgets for both processes have to add up under the cgroup's `memory.max`, with Go's counted at its real single-copy weight. `admission.FitBudget` shrinks the gateway's to fit, and the gateway's high water watches the whole container, so a Node near the limit stops the gateway adding to it.
- **Driver performance.** `modernc.org/sqlite` is pure Go. The `Gateway DB` workflow's bench job times the hot-path queries on it against better-sqlite3 and node:sqlite.

## Later phases

- **Phase 3.** The same providers on `/v1/chat/completions` and `/v1/responses`, with the OpenAI pivot translators the hot traffic uses. `round-robin` and `fusion` combos.
- **Phase 4.** Other API-key providers through the default executor. OAuth providers stay in Node, which owns token refresh, until their refresh logic is ported and holds a cross-process lease in the database.
- **Phase 5.** The Codex WebSocket bridge in Go, replacing the loopback POST with an in-process call.
- Node keeps the dashboard, management APIs, OAuth flows, cloud sync and the long tail of providers for the foreseeable future. The gateway's job is the hot path.

## Rolling back

Set `GATEWAY_MODE=off`, or unset it, and redeploy. Node takes port 20128 again with nothing of the gateway running. No data changes: phase 1 never opens the database, and phase 2b's `native` mode only reads it (apart from SQLite's own checkpoint when the gateway closes it after Node has exited). In phase 2 everything the gateway writes uses Node's own tables and formats. The two rows Node adds to `_meta` (`dbDriver`, `configGeneration`) mean nothing to a Node without them.
